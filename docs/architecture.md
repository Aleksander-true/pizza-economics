# Архитектура

Прототип состоит из пяти частей: данные, расчётный движок, контроллер, интерфейс и сохранение. DOM и localStorage не входят в движок. Серверной части нет.

## 1. Данные

`src/engine/types.ts` задаёт идентификаторы и контракты: `Ingredient`, `Recipe`, `Offer`, `Level`, `Batch`, `PlanEvaluation`, `OptimalPlan`, `Progress`.

`src/data/levels.ts` содержит справочник ингредиентов, рецепты и 12 сценариев. Цена продажи принадлежит паре «рецепт + размер» в конкретном уровне. Стоимость продукта и поставка тоже принадлежат уровню.

`Batch.portions` хранит состав в нормах 15 см. `SIZE_FACTORS` переводит его в физические порции: 15 → 1, 30 → 4, 45 → 9. Благодаря этому размер меняется без накопления ошибок округления.

## 2. Расчётный движок

`src/engine/economy.ts` экспортирует чистые функции:

| Функция | Результат |
| --- | --- |
| `createBatch(id)` | Чистая заготовка на одну пиццу 15 см |
| `evaluatePlan(level, batches)` | Распознанные рецепты, расход, остатки, выручка, расходы, прибыль, причины запрета приготовления |
| `findOptimalPlan(level)` | Максимальная прибыль и один достигающий её план |
| `scorePlan(profit, optimum)` | Число звёзд |

Функции не меняют входные объекты. Деньги и порции целые, поэтому сравнение максимума не требует округления. Причины недопустимости плана типизированы; тексты объяснений принадлежат интерфейсу.

Оптимизатор перебирает допустимые количества каждого варианта «рецепт + размер» с мемоизацией по индексу варианта и остаткам. Это точный поиск, а не жадный выбор самой дорогой пиццы. В каждом рецепте обязательно есть тесто, поэтому перебор конечен. Оптимум кешируется контроллером на время работы приложения.

Алгоритм рассчитан на небольшие учебные поставки. При значительном увеличении запасов, числа продуктов или ограничений следует измерить время поиска, после чего вынести его в Web Worker либо заменить реализацию, сохранив контракт `OptimalPlan`.

## 3. Контроллер

`src/app/controller.ts` создаёт независимый экземпляр контроллера. В него передаются уровни и адаптер сохранения. Интерфейс получает снимок через `getSnapshot()`, подписывается через `subscribe()` и отправляет типизированные команды через `dispatch()`.

Состояния:

| Из | Команда | В | Условие |
| --- | --- | --- | --- |
| Выбор уровней | `open-level` | Планирование | Уровень открыт |
| Планирование | Изменение партии | Планирование | Данные допустимы |
| Планирование | `cook` | Результат | План можно приготовить |
| Результат | `retry` | Планирование | Сохраняется состав текущего плана |
| Результат | `next-level` | Планирование следующего | Получена хотя бы одна звезда |
| Любой экран | `show-levels` | Выбор уровней | — |

Контроллер хранит партии, текущий экран и уровень, лучшие результаты, количество открытых подсказок и состояние показа решения. Суммы и остатки вычисляются из партий, отдельного изменяемого денежного баланса нет.

Приготовление обрабатывается только в состоянии планирования. Повторный клик после перехода на результат не создаёт ещё одну продажу. Сохранение выполняется после расчёта результата, лучшие значения объединяются с предыдущими.

## 4. Интерфейс

`src/ui/view.ts` рисует экраны и связывает события с командами. Выбранная партия, открытая панель рецептов и состояние перетаскивания относятся к представлению, а не к экономике.

Карточки партий имеют постоянные идентификаторы. При пересчёте обновляются изменившиеся карточки; фокус восстанавливается по ключу контрола. Pointer Events обслуживают мышь и касания, обычные кнопки позволяют выполнить те же действия с клавиатуры. Нативный `dialog` обеспечивает модальность рецептов и закрытие по Escape.

`src/ui/art.ts` содержит собственную SVG-графику продуктов и пицц. Внешние изображения, шрифты и сетевые запросы для рисунков не нужны. `src/ui/style.css` задаёт тему «Учебный стол», адаптивную сетку, состояния элементов и режим уменьшенного движения.

Для замены HTML-интерфейса достаточно сохранить команды и подписку контроллера; расчётный код менять не требуется.

## 5. Сохранение

`src/storage/progress.ts` реализует `ProgressStore` поверх переданного объекта Storage. Ключ — `pizza-economics.progress.v1`, формат имеет `version: 1`.

Данные проверяются при чтении. Некорректное или недоступное хранилище не мешает игре: она начинается с пустого прогресса. Ошибка записи показывается на экране результата; текущая сессия остаётся рабочей. При изменении формата следует добавить явную миграцию, а не молча интерпретировать старые данные как новые.

## Как расширять

- **Новый уровень:** добавить описание в `definitions`, доступные рецепты, цены и поставку; пройти смоук-сценарий. Количество карточек и общий максимум звёзд вычисляются из данных.
- **Новый рецепт:** добавить состав в `RECIPES` и предложение цены для доступных размеров. Изменения алгоритма распознавания не нужны.
- **Новый ингредиент:** расширить `INGREDIENT_IDS`, справочник, цены, поставки и SVG-рисунок. Массивы в `amounts()` следуют порядку идентификаторов; при редактировании надо сохранять этот порядок.
- **45 см:** включить размер в данных, задать цены и достаточный запас продуктов. Коэффициент 9 уже есть, но существующие таблицы цен пока рассчитаны на два размера.
- **Предзаказы:** добавить тип ограничений, проверку минимального количества в `evaluatePlan`, учёт этих ограничений в `findOptimalPlan`, отображение в UI. Не ограничиваться проверкой после приготовления.
- **Другая тема:** изменить CSS и SVG. Состояния, рецепты и экономика остаются общими.
- **Другое хранилище:** реализовать `ProgressStore`. Текущий интерфейс синхронный; для удалённого сохранения сначала понадобится асинхронный контракт контроллера.

## Сборка и проверка

`src/main.ts` связывает данные, хранилище, контроллер и UI. `scripts/build.ts` собирает приложение через esbuild. Сборка IIFE позволяет открыть `dist/index.html` напрямую, без сервера ES-модулей. Разработка использует сервер на localhost и watch; после правок страницу нужно перезагрузить.

TypeScript запускается в strict-режиме. По запросу используются только смоук-проверки; сценарий и проверенное окружение описаны в README. Браузерные вспомогательные профили, логи и снимки проверки не входят в исходники, кроме иллюстрации результата `docs/preview.png`.
